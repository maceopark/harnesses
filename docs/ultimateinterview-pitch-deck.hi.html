मूल समस्या

एक उचित अनुरोध दो उचित—पर असंगत—implementations बना सकता है।

“Order creation fail हो तो retry करें।”

Implementation A

हर timeout पर retry। तेज़ और परिचित, लेकिन response खोने पर दो बार charge कर सकता है।

Implementation B

कभी retry नहीं। Duplicate से बचता है, पर vendor द्वारा commit किया order छोड़ सकता है।

Coding model भ्रमित नहीं है। Product decision हुआ ही नहीं।

Material decision loop

क्या दो compliant implementations materially अलग परिणाम दे सकते हैं?

हाँ→केवल उस authority या decision को सुलझाएँ
नहीं→Interview रोकें
Authority उपलब्ध नहीं→Incomplete—अनुमान नहीं

तीन material owner decisions एक soft reassessment point हैं, quota नहीं। साफ अनुरोध zero-question fast path लेते हैं।

कोई link गायब या कमजोर हो, requirement साझा हो, या authority invent हो—projection gate sealed build-contract.json बनाने से मना कर देता है।

decision.jsonl का उपयोग

“Model ने शायद यह चुना” को inspectable evidence में बदलें।

इसके बिना हम हर helper के लिए owner से पूछकर interview monster लौटाते हैं—या implementer को चुपचाप decide करने देते हैं।

Permitted choice action से पहले log होती है: gap, decision, rationale, alternatives, affected paths, observable impact और contract digest.

Code review target करेंहर logged affected_path से शुरू करें।
Claimed impact जाँचेंobservable_impact को actual CLI behavior और tests से मिलाएँ।
Unexplained behavior खोजेंRequirement, delegation या receipt के बिना substantive diff संदिग्ध है।
Regression बनाएँबार-बार होने वाले escapes को tests और future discovery signals बनाएं।

Receipt evidence है, authority नहीं। Product-visible या out-of-delegation choice पर रुककर owner के पास लौटना चाहिए।
