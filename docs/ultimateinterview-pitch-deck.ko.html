Ultimateinterview · 현재 구조

인터뷰 괴물을 만들었다.
그리고 멈추는 법을 가르쳤다.

여러 인터뷰 스킬의 좋은 아이디어를 모아 안전장치를 하나씩 보탰다. 그러다 깨달았다. 필요한 건 질문 하나를 더 하는 일이 아니었다. 모델이 스스로 내린 선택을 기록할 장치였다.

출발점

합리적인 요구 하나에서도 서로 양립할 수 없는 두 구현이 나올 수 있다. 둘 다 나름대로 합리적이다.

"주문 생성이 실패하면 재시도해 주세요."

구현 A

모든 타임아웃에 재시도한다. 빠르고 익숙하지만 응답만 유실된 경우 이중 결제가 발생할 수 있다.

구현 B

절대 재시도하지 않는다. 중복 결제는 막지만 공급자가 이미 접수한 주문을 버릴 수 있다.

코딩 모델이 헷갈린 게 아니다. 아무도 제품 결정을 내리지 않은 것이다.

발명하기 전에 배운 것

다른 인터뷰 스킬을 살펴보고 잘 작동하는 방식만 남겼다.

grilling / grill-me의존관계에 따라 한 번에 하나씩 묻고 의사결정 트리를 따라간다.
grill-with-docs어려운 결정과 도메인 용어를 ADR과 용어집에 남긴다.
Prometheus / ulw-plan질문하기 전에 저장소를 조사하고 인터뷰 맥락 없이도 이해할 수 있는 실행 계획을 만든다.
Claude·Codex 내장 planner저장소에 맞춰 조정하고 실행 환경의 강점을 살린다.

개인적인 사용 경험과 구조 분석을 바탕으로 한 내용이며 통제된 비교 실험은 아니다. Ultimateinterview가 새로 더한 부분은 8번 슬라이드에서 설명한다.

사건 보고서 · 숫자는 실제다

작은 Todo CLI 하나.
리뷰어 3명. 7라운드.

90분

구현을 시작하기 전에 인터뷰에 쓴 시간.

독립 리뷰어 3명각자 다른 종류의 누락을 찾았다.
전체 리뷰 7라운드수정할 때마다 새로운 예외와 준비 상태를 묻는 질문이 이어졌다.
총 21회 리뷰Todo CLI는 여전히 작았지만 검증 절차는 계속 커졌다.

극적 재연 · 숫자는 실제다

모델은 우리가 시킨 일을 정확히 했다. 계속 위험을 찾았다.

요청

"간단한 Todo CLI를 만들어 주세요."

1라운드: 리뷰어 3명이 빠진 경우를 지적한다.
4라운드: 리뷰어들이 그 문제를 고친 방식을 지적한다.
7라운드: 리뷰어들이 이전 코멘트에 대한 코멘트를 다시 리뷰한다.

Todo CLI에는 명령 몇 개가 필요했다. 인터뷰는 여기에 헌법을 붙였다.

진단

문제는 추론 능력 부족이 아니라 끝없는 성실함이었다.

우리가 보상한 것

예외를 하나 더 찾아라. 질문을 하나 더 하라. 리뷰어를 붙여라. 무엇보다 너무 일찍 멈추지 마라.

사용자에게 필요했던 것

구현을 바꾸는 결정만 해결하고 작고 검증 가능한 계약을 넘겨라.

추론 비용이 낮아질수록 언제 멈출지 아는 능력이 더 귀해진다.

물러서지 않고 단순하게

모델의 능력은 그대로 두고 그 주위의 불필요한 절차만 걷어냈다.

인터뷰의 근거는 저장소에서 찾는다

작업을 직접 규정하는 가장 가까운 자료 두세 곳부터 본다.

결정 권한은 owner에게 둔다

답에 따라 동작, 권한, 경계, 실패 처리, 검증이 바뀔 때만 묻는다.

결정의 흐름을 보존한다

결정 → 권한 → 요구사항 → 인수조건 → 검증.

새로운 시선으로 한 번만 점검한다

외부 리뷰어는 한 명, 유효한 blocker는 최대 세 개로 제한한다. 리뷰 의회는 만들지 않는다.

빠져 있던 통제 지점

모델이 조용히 product owner가 되는 순간은 두 번이다.

코딩 전

대화를 인계 문서로 요약하는 과정에서 확정한 결정이 사라지거나 흐려진다.

통제: 권한과 정확한 결정의 흐름을 sealed Build Contract로 컴파일한다.

코딩 중

구현자가 빈틈을 만나 합리적인 선택을 내리지만 나중에는 아무도 그 선택을 확인할 수 없다.

통제: 제한된 재량과 행동 전에 남기는 계약 digest 기반 decision.jsonl 영수증.

컴파일러는 권한 없는 해석을 막고 영수증은 허용된 재량을 감사할 수 있게 한다.

중요 결정 루프

계약을 지키는 두 구현이 중요한 부분에서 달라질 수 있는가?

예→그 결정이나 결정 권한만 확인
아니오→인터뷰 종료
권한을 확인할 수 없음→추측하지 말고 계약을 미완료로 표시

owner가 내려야 할 결정이 세 개 나오면 잠시 멈추고 다시 판단한다. 채워야 할 할당량이 아니라 점검 시점이다. 요청이 명확하면 질문 없이 바로 진행한다.

작은 실행 계약

사람이 읽을 만큼 짧고 컴파일할 만큼 엄격한 단일 기준.

Outcome & Boundaries

목표, 범위, 하지 않을 일.

Decisions & Defaults

각각 하나의 권한만 담은 원자적 DEC-NNN.

Acceptance

입력 → 동작 → 관찰 가능한 성공 → 해당하는 실패.

Verification

인수조건에 연결되고 맥락을 빠짐없이 담은 명령 또는 시나리오.

별도의 모호성 원장이나 질문 점수, 대화 기록 사본, 사람이 중복 작성한 권한 목록은 두지 않는다.

권한 경계

저장소는 현재 상태를 보여 줄 뿐, 제품이 어떤 모습이어야 하는지 결정하지 못한다.

증거일 뿐인 것

현재 동작, 테스트, 문서, 관례, 모델의 추천, 리뷰어의 합의, owner의 침묵.

결정 권한이 있는 것

owner의 명시적인 결정

현재 적용되는 공식 계약

범위가 정해진 위임

합의로 빈틈을 찾을 수는 있지만 답을 승인할 수는 없다.

계약 컴파일이 필요한 이유

매끄러운 요약도 문구 하나를 빠뜨려 제품을 바꿀 수 있다.

컴파일러가 없으면

Owner: “완료 항목은 기본 목록에서 숨긴다.”

Handoff: “Todo 목록을 지원한다.”

Executor: 모든 항목을 표시한다.

Test: 명령이 0으로 끝난다. 통과.

컴파일러가 있으면

DEC-003이 결정 문구를 그대로 보존한다.

하나의 권한을 하나의 REQ에 연결한다.

인수조건으로 완료 항목이 표시되지 않는지 확인한다.

검증 단계에서는 실제 출력값을 검사한다.

연결이 사라지거나 약해진 경우, 여러 요구사항이 권한 하나를 공유하는 경우, 없는 권한을 만들어 낸 경우에는 projection gate가 sealed build-contract.json 생성을 거부한다.

decision.jsonl을 활용하는 법

“모델이 아마 이렇게 정했겠지”라는 추측을 확인 가능한 증거로 바꾼다.

기록이 없으면 helper 이름까지 owner에게 물으며 인터뷰 괴물을 되살리거나 구현자가 아무도 모르게 결정하게 된다.

허용된 선택이라면 행동 전에 빈틈, 결정, 이유, 대안, 영향을 받는 경로, 겉으로 드러나는 영향, 계약 digest를 기록한다.

코드 리뷰의 출발점기록된 모든 affected_path부터 살핀다.
영향 범위 검증observable_impact를 실제 CLI 동작·테스트와 비교한다.
설명되지 않은 동작 발견요구사항·위임·영수증으로 설명되지 않는 중요한 diff는 의심 대상이다.
회귀 방지반복되는 이탈을 테스트와 다음 조사 단계의 신호로 바꾼다.

영수증은 증거이지 권한이 아니다. 제품에 드러나거나 위임 범위를 벗어난 선택은 멈추고 owner에게 돌려보내야 한다.

실제 효용

문서를 위한 문서가 아니다. 의도가 어디서 달라졌는지 찾아내는 장치다.

Sealed contract
기대한 동작→Compiled plan + 영수증
허용된 선택→Diff + tests
실제 동작→Postmortem
빈틈 분류

Contract → implementation

모든 요구사항을 구현하고 직접 검증했는가?

Implementation → contract

중요한 모든 동작을 요구사항, 범위가 정해진 위임, 유효한 영수증 중 하나로 설명할 수 있는가?

이 자료를 맞춰 보면 허용된 변형, 빠진 요구사항, 인계 과정의 손실, 구현 중 의도 변경을 구분하고 가장 먼저 실패한 장치를 고칠 수 있다.

정직한 비교

이 주장의 근거는 실행하지 않은 벤치마크가 아니라 직접 사용한 경험과 구조 분석이다.

능력강한 인터뷰 스킬Ultimateinterview
좋은 질문대체로 매우 강함그 장점을 받아들임
저장소 우선 조사좋은 작업 흐름에 흔함brownfield에서는 필수
예외사항 검토주요 강점중요할 때만 사용
멈출 시점판단이나 prompt 관례에 맡기는 경우가 많음명시적인 반사실 종료 테스트
구현 중 임의 선택 공개맥락이나 산문에만 남기 쉬움행동 전에 남기는 계약 digest 기반 결정 영수증
handoff 뒤 의도 변경 탐지같은 맥락에 의존하기 쉬움독립적인 양방향 계약 감사

Ultimateinterview가 더한 것

더 좋은 질문을 발명한 것이 아니다.
모델의 재량을 검사할 수 있게 만들었다.

다른 스킬들은 모델에게 조사하는 법을 가르쳤다. Ultimateinterview는 모델의 권한을 좁게 정하고 명확한 종료 규칙을 두며 모델이 내린 선택을 기록한다. 이 기록을 보면 구현이 어느 순간 제품 설계로 바뀌었는지 알 수 있다.

단순한 버전이 더 강한 이유는 결과를 바꿀 수 있는 불확실성에만 집중하기 때문이다. 모델이 즉석에서 선택해야 할 때는 증거를 남긴다.

결론

최고의 인터뷰어는
입을 다물 때를 안다.
그리고 영수증을 남긴다.

Ultimateinterview를 쓸 때

세션 간 handoff가 있거나 돈, 데이터, 권한, 호환성, 실패 동작, 되돌릴 수 없는 변경을 다루는 작업에 쓴다. 드러나지 않는 제품 결정 하나가 큰 비용으로 이어질 수 있는 작업을 위한 도구다.

가벼운 planner를 쓸 때

오타 수정, 되돌릴 수 있는 refactor, 기계적인 업데이트, 이미 공식 계약으로 정의된 작업에는 가벼운 planner가 낫다.
