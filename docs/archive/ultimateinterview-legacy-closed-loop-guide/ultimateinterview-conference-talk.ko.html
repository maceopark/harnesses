질문 1 · 선택지보다 근거가 먼저

재시도 설정 전에 금전 상태부터 묻습니다.

근거: 호출자에는 안정적인 client_order_id가 있지만, 게이트웨이는 벤더에 Idempotency-Key를 보내지 않습니다.

상황: 벤더가 O-481을 만들고 고객에게 청구한 뒤, 서비스가 응답을 받기 전에 연결이 끊어졌습니다. 같은 논리적 요청을 재시도하면 반드시 어떻게 되어야 합니까?

  1. 기존 주문을 반환하고, 주문과 결제를 절대 두 번 만들지 않는다 — 권장. 벤더 계약과 로컬 식별자가 뒷받침합니다.
  2. 알 수 없음/처리 중을 반환하고 재시도하지 않는다. 별도의 정합성 복구 담당자가 필요합니다.
  3. 새 주문으로 재시도하고 중복을 허용한다. 처음 제시한 실패 우려와 충돌합니다.
  4. 기타: 자유롭게 다른 답을 쓸 수 있어야 합니다.

반증 조건: 중복 생성이 허용되거나, 다른 시스템이 이미 정합성 복구를 보장합니다.

REQ 식별자는 결정을 보존하고, VER은 비즈니스 효과를 관찰합니다.

REQ-001 재시도 경계

선택된 실패만, 안정적인 키로, 추가 시도 최대 2회, 최초 호출 안에서만 재시도.

기존 주문 반환. 로컬 주문, 벤더 주문, 결제는 각각 하나.

REQ-003 페이로드 충돌

정규화된 페이로드가 바뀌면 409 반환. 두 번째 벤더 POST는 없음.

REQ-004 동시성

동일한 동시 페이로드는 하나의 주문 ID로 수렴하고, 개수는 모두 하나로 유지.

REQ-005 남은 시간 예산

지연 + 600ms 전체가 2초 데드라인 안에 들어갈 때만 429 재시도 시작.

VER-ORDER-COMMIT-DROP

키 K로 주문 O를 커밋하고 응답을 끊은 뒤 재시도해 결과 R을 캡처하고 영속 상태를 조회합니다. R == O이며 세 개수가 모두 1이어야 합니다.

실제 클라이언트가 시도마다 새 키를 보내는 동안에는 mock 호출 횟수만 맞춰도 이 오라클을 통과할 수 없습니다.

의미는 소유하고, 실행 수단은 빌린다

실행까지 소유하면 우리가 측정하려는 신호가 오히려 약해집니다.

확증 결합

하나의 컨텍스트가 코딩 도중 빠진 규칙을 조용히 채우고, 자신의 선택을 요구 사항이라고 설명한 다음, 그 선택을 정답으로 만드는 테스트까지 쓸 수 있습니다.

어댑터 유지보수의 늪

런타임마다 워크트리, 권한, 샌드박스, 배포, 복구, 도구를 다시 만드는 일은 더 좋은 요구 사항을 발견하지 못합니다.

네이티브 런타임의 이점

Claude, Codex, CI, 사람으로 구성된 팀은 이미 자신의 실행 방식과 실패 복구를 알고 있습니다.

이식 가능한 반사실 검증

새 빌더는 검토된 계약만 보고도 같은 관찰 가능한 동작을 만들어야 합니다. 그렇지 않으면 차이를 반환해야 합니다.

프로토콜은 의미와 인수 조건을 소유합니다. 구현 수단은 이미 그것을 소유한 환경에서 빌립니다.

경계일 뿐, 측정을 금지하는 것은 아니다

인터뷰는 제품 실행자가 되지 않고도 의미를 측정할 수 있습니다.

프로토콜이 소유하는 것

  • 저장소 근거, 원장, 질문, 압박, 제한된 L0–L3 프로브
  • 저장소 내부 allowlist에 한정된 safe-auto 검증 캡처
  • BuildContract, 안정적인 REQ/VER 식별자, 다이제스트
  • ExecutionReturn, 결정, 근거 비교, 사후 검토, 다음 세션의 학습

프로토콜이 소유하지 않는 것

  • 범위가 열려 있는 구현이나 제품 수정
  • 배포, 롤백, 오케스트레이션, 지속되는 실험
  • 임의 셸 실행이나 런타임별 복구
  • 규제 증명, 운영 텔레메트리 보관 책임, 강한 샌드박스 보장

타입이 있는 산출물은 주장을 제한하지만, 임의 실행자를 신뢰할 수 있게 만들지는 못합니다. 더 높은 보증이 필요한 환경에는 여전히 실행을 소유하는 제어 계층이 필요합니다.

결론

같은 LLM 지능.
더 낮은 프로세스 편차.

이 비용을 지불할 때

돈, 데이터, 권한, 호환성, 네트워크 모호성, 동시성, 레거시 시스템, 세션 간 인계, 속이기 쉬운 테스트가 걸려 있을 때.

가벼운 플래너로 충분할 때

오타, 되돌리기 쉬운 로컬 리팩터링, 기계적인 의존성 변경, 권위 있는 테스트 계약이 이미 작업을 제한하고 있을 때.

모델은 위험한 가능성을 생성하는 데 사용합니다. 로컬 근거와 결정 권한은 그 가능성을 확정하는 데 사용합니다. 새로운 빌더와 이후의 실행 근거에는 인터뷰가 틀렸음을 증명할 기회를 줍니다.
