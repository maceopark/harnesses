Question 1 · options से पहले evidence

Retry settings से पहले financial state पूछें।

Evidence: caller में stable client_order_id है; gateway vendor Idempotency-Key नहीं भेजता।

Scenario: vendor O-481 बनाकर charge करता है, फिर response से पहले connection close होता है। Retry पर क्या होना चाहिए?

  1. Original order लौटे; duplicate order/charge कभी नहीं — Recommended. Vendor contract और local identity से supported।
  2. Unknown/pending लौटे; retry नहीं। Reconciliation owner चाहिए।
  3. New order बनाकर duplicate tolerate करें। Stated failure fear से conflict।
  4. Other: free-form escape hatch।

Falsifier: duplicate acceptable है, या दूसरा system reconciliation guarantee करता है।

Interview output

REQ identities decisions को सुरक्षित रखती हैं; VER business effect को observable बनाती है।

REQ-001 retry boundary

Selected failures, stable key, अधिकतम दो further attempts और केवल original invocation।

REQ-002 post-commit result

Original order तथा ठीक एक local row, vendor row और charge।

REQ-003 payload conflict

Changed canonical payload पर 409; दूसरा vendor POST नहीं।

REQ-004 concurrency

Equal concurrent payloads एक order ID पर converge हों; सभी counts एक रहें।

REQ-005 budget

429 को तभी retry करें जब delay और अगली पूरी 600 ms window, 2 s deadline में fit हों।

VER-ORDER-COMMIT-DROP

Key K से order O commit करें, response drop करें, retry के बाद result R लें; durable state में R == O हो और तीनों counts 1 हों।

यदि real client हर attempt पर नई key भेजता है, तो केवल mock call-count पर आधारित oracle इस defect को पकड़ नहीं सकता।

Bounded challenge · readiness reversible है

पहला draft complete लगता है, फिर भी उसमें gaps होते हैं।

L0 · fresh static reading

यह merchant scope, undefined payload equality, oversized Retry-After और gameable mock oracle खोजता है।

L1 · two independent stubs

DB-backed commit-close fake duplicate rows दिखाती है; barrier-based concurrent fake changed-payload race दिखाती है।

Material divergence gap को दोबारा खोलती है: dry-sweep streak clear होती है, checkpoint stale और reviewed contract invalid होते हैं तथा interview फिर शुरू होता है।

Neutral rerun केवल probe sequence बंद कर सकता है; उसे zero completeness credit मिलता है। “यहाँ और कुछ नहीं मिला” का अर्थ “कुछ और नहीं है” नहीं होता।

Adapter treadmill

Portable counterfactual

Protocol meaning और acceptance का उत्तरदायित्व लेता है; implementation mechanics उस environment पर छोड़ता है जो उन्हें पहले से संभालता है।

Protocol का उत्तरदायित्व

  • Repo evidence, ledger, questions, pressure और bounded L0–L3 probes
  • Repo-local, allowlisted safe-auto verification capture
  • BuildContract, stable REQ/VER identities और digest
  • ExecutionReturn, decisions, evidence comparison, postmortem और अगला lesson

Protocol के उत्तरदायित्व से बाहर

  • Open-ended implementation या product edits
  • Deployment, rollback, orchestration या persistent experiments
  • Arbitrary shell execution या runtime-specific recovery
  • Regulated attestation, production telemetry custody या hard sandbox guarantee

Typed artifacts claims को constrain करते हैं; वे किसी arbitrary executor को trustworthy नहीं बना सकते। High-assurance environment को अब भी execution-owning control plane चाहिए। Closed loop secondary है, लेकिन execution को interview का model falsify करने देने के लिए आवश्यक है।
