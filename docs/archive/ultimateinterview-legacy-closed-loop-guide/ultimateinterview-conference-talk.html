Question 1 · evidence before options

Ask about the financial state before retry settings.

Evidence: the caller has stable client_order_id, but the gateway sends no vendor Idempotency-Key.

Scenario: the vendor creates O-481 and charges the customer, then the connection closes before our service receives the response. When the same logical request is retried, what must happen?

  1. Return the original order; never create or charge twice — Recommended. Supported by the vendor contract and local identity.
  2. Return unknown/pending and do not retry. Requires a reconciliation owner.
  3. Retry as a new order and tolerate a duplicate. Conflicts with the stated failure fear.
  4. Other: preserve the free-form escape hatch.

Falsifier: duplicate creation is acceptable, or another system already guarantees reconciliation.

The interview output

REQ identities preserve decisions; VER observes the business effect.

REQ-001 retry boundary

Selected failures only; stable key; at most two further attempts; original invocation only.

REQ-002 post-commit result

Return original order; one local row, vendor row, and charge.

REQ-003 payload conflict

Changed canonical payload returns 409; no second vendor POST.

REQ-004 concurrency

Equal concurrent payloads converge on one order ID; counts remain one.

REQ-005 remaining budget

Start a 429 retry only when delay + full 600 ms fits the 2 s deadline.

VER-ORDER-COMMIT-DROP

Commit order O under key K, drop the response, retry, capture result R, then query durable state: R == O and all three counts equal 1.

A mock call count cannot satisfy this oracle while the real client emits a new key per attempt.

Bounded challenge · readiness is reversible

The first draft still sounds complete—and still has holes.

L0 · fresh static reading

Finds merchant scope, undefined payload equality, oversized Retry-After, and a gameable mock oracle.

L1 · two independent stubs

A DB-backed commit-close fake exposes duplicate rows. A barrier-based concurrent fake exposes changed-payload races.

Material divergence reopens the gap: clear the dry-sweep streak, stale the checkpoint, invalidate the reviewed contract, and return to the interview.

A targeted neutral rerun may close this probe sequence. It earns zero completeness credit; “we found nothing else here” never means “nothing else exists.”

Own semantics · rent mechanics

Execution ownership would weaken the signal we are trying to measure.

Confirmation coupling

One context can silently fill a missing rule while coding, describe its own choice as required, then write a test around that choice.

Adapter treadmill

Rebuilding worktrees, permissions, sandboxes, deployments, recovery, and tools for every runtime does not discover better requirements.

Native runtime advantage

Claude, Codex, CI, and human teams already know their execution mechanics and failure recovery.

Portable counterfactual

A fresh builder must produce the same observable behavior from the reviewed contract—or return a deviation.

The protocol owns meaning and acceptance. It rents implementation mechanics from the environment that already owns them.

A boundary, not a ban on measurement

The interview may measure semantics without becoming a product executor.

Protocol owns

  • Repository evidence, ledger, questions, pressure, and bounded L0–L3 probes
  • Repo-local, allowlisted safe-auto verification capture
  • BuildContract, stable REQ/VER identities, and digest
  • ExecutionReturn, decisions, evidence comparison, postmortem, and next-session lesson

Protocol does not own

  • Open-ended implementation or product edits
  • Deployment, rollback, orchestration, or persistent experiments
  • Arbitrary shell execution or runtime-specific recovery
  • Regulated attestation, production telemetry custody, or a hard sandbox guarantee

Typed artifacts constrain claims; they cannot make an arbitrary executor trustworthy. Higher-assurance environments still need an execution-owning control plane.

Takeaway

Same LLM intelligence.
Lower process variance.

Pay the overhead

Money, data, permissions, compatibility, network ambiguity, concurrency, old systems, cross-session handoff, or gameable tests.

Use a lighter planner

Typos, reversible local refactors, mechanical dependency changes, or work already constrained by an authoritative test contract.

Use the model to generate dangerous possibilities. Use local evidence and decision authority to settle them. Let a fresh builder—and later execution evidence—prove the interview wrong.
