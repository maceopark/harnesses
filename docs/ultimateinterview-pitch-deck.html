Ultimateinterview · current architecture

We built an interview monster.
Then taught it when to stop.

We borrowed the best ideas from other interview skills and turned every safety dial to eleven. Eventually, we realized the missing feature was not another question. It was a record of every choice the model made on its own.

The original problem

One reasonable request can lead to two reasonable but incompatible implementations.

"Retry failed order creation."

Implementation A

Retry every timeout. It is quick and familiar, but a lost response could result in a second charge.

Implementation B

Never retry. That prevents duplicate charges, but it may abandon an order the vendor already accepted.

The coding model is not confused. No one made the product decision.

Learn before inventing

I studied other interview skills and kept what worked.

grilling / grill-meAsk one dependent question at a time and follow the decision tree.
grill-with-docsPreserve hard decisions and domain language in ADRs and a glossary.
Prometheus / ulw-planInspect the repository before asking questions, then write a plan that makes sense without the interview context.
Native Claude and Codex plannersAdapt to the repository and use the strengths of the execution environment.

This is based on personal use and structural analysis, not a controlled comparison. Slide 8 introduces what Ultimateinterview adds.

Dramatic reenactment · the counts are real

The model did exactly what we asked: keep looking for risk.

Request

"Build a simple Todo CLI."

Round 1: three reviewers challenge the missing cases.
Round 4: they challenge the fixes for those cases.
Round 7: they review comments about their earlier comments.

The Todo CLI needed a few commands. The interview gave it a constitution.

The diagnosis

The problem was not poor reasoning. It was obedience without a limit.

What we rewarded

Find another edge case. Ask one more question. Add a reviewer. Above all, do not stop too soon.

What the user needed

Resolve the decisions that could change the implementation, then hand off a small contract that can be tested.

When reasoning is cheap, knowing when to stop becomes the hard part.

Simplify without backing down

We kept the model's capabilities and cut the ceremony around them.

Ground the interview in the repository

Inspect the two or three nearest sources that govern the work.

Keep decisions with the owner

Ask only when the answer could change behavior, authority, boundaries, failure handling, or verification.

Preserve decision lineage

Decision → authority → requirement → acceptance → verification.

Run one fresh handoff check

Use one outside reviewer and allow at most three valid blockers, not a review parliament.

The missing control plane

The model can quietly take over product decisions at two points.

Before coding

A decision can disappear or lose force when the conversation becomes a handoff.

Control: compile each decision and its authority into a sealed Build Contract.

During coding

The implementer finds a gap and makes a reasonable choice that no one can inspect later.

Control: limit that discretion and require a digest-bound decision.jsonl receipt before acting.

The compiler prevents unauthorized changes in meaning. The receipt leaves a trail for choices the model was allowed to make.

Material decision loop

Could two compliant implementations differ in a way that matters?

Yes→Resolve that decision or its authority
No→Stop interviewing
No authority available→Mark the contract incomplete instead of guessing

After three owner decisions, the interviewer pauses to reassess. That is a checkpoint, not a quota. A clear request can take the fast path with no questions at all.

A small execution contract

The source of truth is short enough to read and precise enough to compile.

Outcome & Boundaries

The goal, what is in scope, and what is not.

Decisions & Defaults

One decision per DEC-NNN row, with one authority for each.

Acceptance

Input → action → observable success → applicable failure.

Verification

Self-contained commands or scenarios tied to each acceptance case.

There is no separate ambiguity ledger, question score, transcript snapshot, or duplicate authority register written by hand.

The authority boundary

The repository tells us what exists. It does not decide what the product should become.

Evidence only

Current behavior, tests, docs, conventions, model recommendations, reviewer consensus, and silence from the owner.

Sources of authority

An explicit owner decision

An applicable canonical contract

A bounded delegation

Consensus can reveal a gap. It cannot decide how to fill it.

Why compile the contract?

A polished summary can drop one phrase and change the product.

Without the compiler

Owner: "Hide completed todos by default."

Handoff: "Support listing todos."

Executor: lists everything.

Test: command exits 0. Pass.

With the compiler

DEC-003 preserves the exact decision.

One source of authority maps to one REQ.

The acceptance case checks that completed items are absent.

Verification asserts the command's actual output.

If a link disappears, grows weaker, shares a requirement, or invents authority, the projection gate will not produce a sealed build-contract.json.

Using decision.jsonl

The receipt replaces "the model probably chose this" with evidence we can inspect.

Without it, we have two bad options: ask the owner about every helper and bring the interview monster back, or let the implementer make silent choices.

Before acting, the model logs the gap, its decision and rationale, the alternatives it considered, affected paths, observable impact, and contract digest.

Focus the code reviewStart with each logged affected_path.
Check the claimed impactCompare observable_impact with the CLI's behavior and tests.
Find unexplained behaviorA substantive diff without a requirement, delegation, or receipt deserves scrutiny.
Prevent regressionsTurn repeated escapes into tests and signals for future interviews.

A receipt is evidence, not authority. If a choice affects the product or exceeds the delegation, work stops and returns to the owner.

These artifacts show us where the implementation stopped matching the intent.

What Ultimateinterview adds

I did not invent better questions.
I made the model's discretion inspectable.

Other skills taught the model how to investigate. Ultimateinterview draws a narrow boundary around its authority, gives it a deterministic stop rule, and records the choices it makes. That record shows us when implementation has quietly turned into product design.

The simpler version is stronger because it focuses on uncertainty that can change the result. When the model does need to improvise, it leaves evidence behind.

Takeaway

The best interviewer knows
when to shut up.
It also keeps receipts.

Use Ultimateinterview

Use it for handoffs across sessions, or when the work touches money, data, permissions, compatibility, failure behavior, or irreversible changes. It is for tasks where a silent product decision would be expensive.

Use a lighter planner

Use one for typos, reversible refactors, mechanical updates, or work already defined by an authoritative contract.
