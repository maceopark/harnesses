# Ultimateinterview

Run a requirements interview that treats code, docs, logs, domain flow, stakeholder viewpoints, failure modes, and user judgment as separate evidence channels. The goal is a draft spec that can survive a seed-readiness audit when risk warrants it. Enumerate gaps with lenses, then hunt unknown unknowns by proposing falsifiable statements and watching where they collide with evidence.

This file is the runtime: the phase map, the per-round loop, and the invariants. Method detail lives in `references/` and is read at the phase that needs it - the read instructions below are mandatory steps, not suggestions.

## Phase Map

| Phase | Enter when | Do |
| --- | --- | --- |
| ORIENT | skill start | Scan `.ultimateinterview/` for session folders without `handoff.md` and offer to resume the most recent before starting a new one. Then read `references/orientation.md` and follow it: classify, inspect repo + lessons, create persisted session state via `scripts/session_init.py`, choose depth. |
| DUMP + FRAME | session state initialized | Per `references/orientation.md`: brain-dump invitation bundled with the depth calibration (or waiver / context-first checkpoint), then the framing challenge. |
| LOOP | framing recorded | Read `references/interview-loop.md` once, then run the Per-Round Loop below until the stop condition. Lens methods load from `references/lenses.md` as techniques activate. |
| ENDGAME | stop condition met; a readiness-gate trigger fires (`full` depth; a score `3` near handoff; a behavior/data/security-changing score `2`; the output seeds another agent or team; security/privacy, data/schema, irreversible writes, external integration, performance/reliability, or multi-stakeholder workflow touched); or the user asks for independent gating / seed readiness | Read `references/handoff-sequence.md`; execute the canonical pre-handoff sequence (flush → missing sweep/probe → checkpoint → gates + audit → build contract → handoff) in the same turn. |

At any phase:

- If the user abandons ("enough, just build it"), do not exit empty-handed: write `handoff.md` marked `DRAFT - abandoned at interaction N` with the current Build Contract (shape: `references/handoff-sequence.md` §Output Contract), every open score `2`/`3` gap listed under deferred risks as unresolved, and a one-line list of the gates that were skipped.
- Do not implement inside `ultimateinterview` unless the user explicitly exits the interview and asks you to code.
- If asked how this differs from other interview tools, read `references/comparison.md`.

## Core Rule

Do not ask the user for facts the repo can answer. Inspect first, let the user narrate before you interrogate, then ask the single highest-leverage human-decision question. Batch evidence probes into few tool calls; delegate longer probe chains to a read-only subagent returning conclusions plus minimal evidence rows, keeping raw outputs out of the interview context. Probe conclusions enter the ledger under the channel of their evidence source (a delegated repo walk is `from-code`, not `from-research`). Every settled requirement must carry one of the six evidence channels. Treat every substantive user answer as a claim, and pressure-test the ones that carry implementation risk.

## Invariants (every turn)

- Session state: persist `ledger.json` (the evidence ledger - single source of truth for scoring), `protocol.json` (what the interview has actually executed), `questions.json` (latest scored candidates), and append-only `transcript.md` (`references/transcript-format.md`) under repo-root `.ultimateinterview/<slug>/` (kebab-case slug). After each answer, ONE bookkeeping pass - one `session_update.py` delta call covering all session-file updates and ending with the dashboard line; mid-walk discoveries fold into the same pass. Never quote file contents back into the conversation - the dashboard line is the only echo. A protocol step not recorded in `protocol.json` did not happen. Schemas, crash/resume, language, and environment rules: `references/state-files.md`.
- After context summarization or a long gap, reload `ledger.json`, `protocol.json`, `questions.json`, and the transcript tail as the source of truth; conversation memory is not trusted. On resume, determine the phase from `protocol.json` flags and re-read that phase's references before continuing.
- Evidence channels (closed vocabulary; scripts reject anything else): `from-code`, `from-docs`, `from-user`, `from-research`, `from-scenario`, `assumption`. Channels name the evidence source, not the elicitation: a user answer is `from-user` even when a scenario question prompted it - two user statements are one channel and never a triangulation pair; `from-scenario` means a scenario actually walked against the repo or a running system, constraining the entry independently of the user's judgment; `assumption` never counts as an evidence channel. Record channels on every entry you settle; the script counts distinct channels.
- Ledger entries carry a unique `id`, `ambiguity_score` (`0` settled with evidence, `1` low - assumption accepted, `2` medium - implementation could branch, `3` high - unsafe to code), `impact_weight` (`1` low, `2` moderate, `3` high, `5` critical), `status` (`Draft`, `Triangulated`, `Contested`, `Blocked`, `Accepted`, `Deferred`), `evidence_channels`, and `origin` (the mechanism that surfaced the entry: `orientation`, `dump`, `scored-question`, `pressure`, `batch`, `checkpoint`, `sweep`, `contrarian`, `lens:<name>`, `fold-back` - for postmortem attribution).
- Budget: an interaction is one round-trip to the user - it counts user interruptions, not question marks. The costing table (which events cost 1 vs 0, and the up-to-two-free-pressure-follow-ups-per-thread rule) lives with the typed events in `references/state-files.md`. NEVER hand-set counters: pass the typed `event` in the delta and the script computes them all.
- At budget, stop ordinary questioning: present the remaining gaps, ask the user to defer them (owner/date) or explicitly extend - never silently continue (`--next` fires this obligation).
- While interviewing, a turn's visible output is the dashboard line plus the question (or batch) - no unsolicited narrative synthesis (rule-mandated outputs are exempt).
- Self-referential interviews (the subject is this skill or its own files): the skill's prose is `from-docs` evidence, never ground truth - executing the scripts and tests is the `from-code` channel; fresh-context gates must go to a subagent (a self-audit of your own program is circular).
- Subagent naming (cross-vendor routing): dispatch every subagent this skill spawns (fresh-context reviewer, fresh-implementer test, advisory lanes `repo-prober`/`contrarian`/`question-scout`/`implementer-scout`, slim contrarian review) through the harness task tool with the agent name `critic` — a read-only role. Keep each lane's functional role in its per-task prompt, never the agent name, so a `task.agentModelOverrides["critic"]` binding can route these read-only lanes to a cross-vendor model without changing the interview model.

## Deterministic Helpers

Never calculate script outputs mentally - use the scripts whenever the state can be represented as JSON.

- `scripts/session_init.py <repo-root> <slug> --entries '<json array>'`: ORIENT initializer - already-valid state files, fresh-suffix rule, `.gitignore` coverage.
- `scripts/session_update.py <session-dir> --delta '<json>'`: the whole bookkeeping pass in ONE validated call - typed `event` (computes every counter), entry set/add (pressure gate), `checkpoint_confirm` crediting, lens merges, history append, `transcript` append with the computed interaction number - and emits the dashboards (`--next` appends routing). PREFERRED writer; hand-edit only what a delta cannot express.
- `scripts/session_status.py <session-dir>`: read-only dashboards + `Due Now` + warnings + ready line. `--next`: deterministic next-action routing - obey like Due Now; its critical-path call is a floor (escalate freely, never demote). `--gate`: endgame hard checks (unresolved Contested, deferrals without owner/date; exit 1 blocks).
- `scripts/ambiguity_ledger.py`/`scripts/protocol_state.py`: per-file checks. `scripts/question_score.py`: the exact converge formula (`references/interview-loop.md`). `scripts/transcript_check.py`: transcript↔protocol consistency (pre-handoff and post-resume). `scripts/lessons.py`: Fired/Caught + auto-retirement. All fail closed - follow the one-line error.
- `scripts/handoff_coverage.py <session-dir>`: pre-handoff ledger→Build-Contract traceability gate. Every settled weight-`2`-or-higher non-deferred ledger entry id must be cited in Part 1 of `handoff.md` (fail-closed, exit 1 otherwise). It is the deterministic floor under the non-deterministic behavior-fidelity rule (`references/handoff-sequence.md`): it proves no settled entry vanished untraced, but a human/reviewer still confirms each cited REQ reproduces the entry's FULL enumerated behavior (synthesis-loss).
- `scripts/verification_lint.py <session-dir>`: post-draft check that every Part-1 command head resolves on this host's PATH. Advisory by default (`--strict` blocks); catches spec-portability defects like `python` vs `python3`.

Handoff readiness is blocker-based: `handoff_ready` is `yes` exactly when no active score `2`/`3` gap remains and every weight-5 settlement is triangulated (two distinct channels) or explicitly `Accepted` on a non-`assumption` channel. Readiness, triangulation, and the waiver are the script's semantics - do not re-derive them. The percentage is informational only - never gate handoff on it.

The stop condition, not a suggestion: the combined `ready: yes` line - `handoff_ready` while the protocol blockers are empty or only the untested build contract (the handoff sequence itself drafts and tests it).

Run from the skill directory or with absolute paths: `uv run scripts/session_status.py --format markdown <repo-root>/.ultimateinterview/<slug>`

## Per-Round Loop

1. `Process the answer` with Answer Handling (below), then the one bookkeeping pass; end it with the dashboard line: residual + top 1-3 drivers (recompute after every answer and every material repo/research discovery; `residual = sum(impact_weight * ambiguity_score)` over active gaps; deferred gaps are excluded but listed under deferred risks with owner/date).
2. `Obey Due Now / --next` before any scored question: the `--next` routing resolves obligations in the fixed order (residual-history lag, budget exhaustion, overdue sweep, stagnation escalation - contrarian probe or checkpoint instead of a scored question; a rising residual from newly found gaps is productive divergence, not stagnation, and the script encodes that veto). Take its first action; you may escalate beyond it, never skip it. Increment `due_now_corrections` when an obligation preempts your planned action. Sweep, checkpoint, and contrarian methods: `references/interview-loop.md`.
3. `Diverge when armed`: re-run an affected lens when an answer contradicts prior evidence, a new module, stakeholder, or lifecycle state appears, or a sweep finds an unvisited track. When two consecutive sweeps produce no new gap, record `divergence: dry` in the ledger - that, not fatigue, ends enumeration. Technique routing: `references/interview-loop.md`; methods: `references/lenses.md`.
4. `Select by criticality`: a gap is `critical-path` when it touches a weight `3`/`5` entry, would settle a score `3` gap, genuinely branches the implementation, contradicts existing evidence, or would narrow scope. Critical-path gaps get the top-ranked question, one at a time, full adaptivity - except up to three MAY share one structured multi-question round-trip (costs 1 interaction) when ALL hold: mutually independent (answers cannot constrain each other), each option space evidenced, each with a recommended default; never bundle gaps whose answers could interact. Everything else (weight `1`/`2` confirmations, preferences, repo-suggested defaults) accumulates into a smart-default batch (composition: `references/interview-loop.md`); never put a critical-path gap in a batch, and never batch while one is open and askable. Flush rule: when no critical-path gap is askable and batchable gaps are pending, send the batch even below 3 items; always flush before the pre-handoff checkpoint.
5. `Checkpoint triggers`: run a falsification checkpoint as the first user interaction on context-first entry; at a sweep when several pending questions score low and one synthesis is cheaper for the user; on stagnation escalation; and mandatorily once before the readiness gate and handoff. Pattern and fatigue rules: `references/interview-loop.md`; crediting: Checkpoint Invariants below.
6. `Contrarian minimum`: at least one contrarian probe per interview before handoff, independent of stagnation; pair it with the mandatory pre-handoff checkpoint if no earlier moment was natural. Log its outcome even when it changes nothing.
7. `Score and ask`: rank candidates with `scripts/question_score.py`; regenerate `questions.json` only when the gap set changed (a gap opened, a critical-path gap settled, or 3+ rounds since last scoring) - otherwise reuse the previous ranking minus answered items. Prune questions the repo can answer, duplicates, non-implementation-affecting ones, and low-confidence speculation. Ask every scored choice and batch through the harness's structured-question tool - its built-in freeform Other is the always-open escape hatch. Default to the structured UI for any user interaction whose answer space is enumerable, the falsification checkpoint included (Other carries corrections; shaping in `references/interview-loop.md`). Stay UI-less only where the step is inherently open narration: the brain-dump invitation, and a pressure or checkpoint follow-up that needs a story (example, walkthrough, evidence). Options from an evidenced space (code, docs, the user's own dump) may carry a recommendation; invented ones are labeled suggestions and never recommended. Prefer a scenario question over an abstract one. Shaping detail: `references/interview-loop.md`. After sending the question, dispatch background advisory lanes (`references/interview-loop.md` §Advisory lanes) so findings are ready when the answer lands.
8. `Stop`: when the stop condition (Deterministic Helpers) is met, the next action - same turn - is ENDGAME (`references/handoff-sequence.md`), not another summary.

## Answer Handling

Between asking a question and rescoring the ledger, process every answer with these rules:

1. `Pressure where it pays`: an answer must survive one pressure follow-up before its gap can drop below score `2` when the answer settles a weight `3`/`5` gap, collapses a score `3` gap, contradicts `from-code`/`from-docs` evidence, narrows scope or artifact class, or is hedged ("probably", "I think", "usually"). Ask for a concrete example or evidence, probe the assumption that makes the answer true, force a boundary (what would you explicitly not do?), or stress it with one scenario. Corroboration by a second evidence channel counts instead of a follow-up. Outside those triggers - low-weight preferences, confirmations of repo-derived defaults, quick picks - settle directly with the evidence channel recorded. Script-enforced: settling a weight-3+ from-user entry below `2` on a single channel needs the op's `pressure` token (`survived`|`second-channel`|`exempt:<reason>`).
2. `Stay deep`: do not rotate to the next scored question while the current answer is still vague. Stay on the thread until the answer names a trigger, a boundary, or observable evidence - within the free-follow-up cap (Invariants); a thread still vague past the cap records its entry at the current score and returns to the question queue.
3. `Preserve nuance`: when an answer carries reasoning, constraints, or scope statements beyond the direct decision, decompose it into separate ledger entries (decision, reasoning, user-stated constraints, user-stated non-goals). If you compressed a rich answer, show the decomposition and ask whether anything was lost.
4. `Collide evidence`: if a user claim contradicts `from-code` or `from-docs` evidence, do not silently pick one. Present both sources, mark the entry `Contested`, and ask which governs.
5. `Triangulate critical entries`: an `impact_weight` `5` entry cannot reach score `0` on a single evidence channel. Require a second channel or the user's explicit single-source acceptance recorded in the ledger as `Triangulated` or `Accepted` accordingly. The script enforces triangulation from recorded channels, not the status label.
6. `Guard intent`: if a candidate option or recommendation would narrow a previously settled scope, artifact class, or outcome - or expand it beyond the stated need - label it `scope reduction` or `scope addition`, never mark it recommended, and require an explicit user decision.
7. `Pivot protocol`: when an answer changes the artifact class or outcome, re-run the framing challenge against the new problem statement, re-scan lens triggers, re-check depth/budget fit, and mark superseded entries in the same bookkeeping pass.

## Checkpoint Invariants

- Tag each checkpoint statement with the ledger id(s) it covers. On a decisive, non-fatigue confirmation, record `from-user` corroboration on covered entries that had a single evidence channel - this can complete weight-5 triangulation; a fatigue-flagged reflexive "all correct" is never credited. Apply via the `checkpoint_confirm` delta (`{ids, fatigue}`) - crediting and counters land mechanically.
- Feed every correction back into the ledger as a new or `Contested` entry. A correction to a statement you believed settled is an unknown unknown surfacing - flip the affected lens back to `triggered` in `protocol.json` and re-run it before returning to scored questions.
