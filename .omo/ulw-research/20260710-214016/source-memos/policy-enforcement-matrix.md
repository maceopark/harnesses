# Ultimateinterview PDP/PEP transition and enforcement map

Research date: 2026-07-10. Read-only inspection of the live `.agents/skills/ultimateinterview` contract and scripts. Focused executable check: `uv run --python 3.14 --with pytest --with pydantic --with rich --with typer pytest -q scripts/test_v1_gate_integration.py scripts/test_v1_session_integration.py scripts/test_v1_protocol_integration.py scripts/test_v1_probe_integration.py` -> `16 passed`.

## Bottom line

Ultimateinterview has a strong **canonical state-writer PEP** and a strong **opt-in final gate**, but it does not have universal mediation. `session_update.py` rejects invalid typed state transitions and atomically commits accepted ones; `session_status.py --gate` evaluates the composite readiness policy and exits `1` on denial. In contrast, `session_status.py --next` only recommends the next action, and no wrapper prevents an agent from asking a different question, writing/delivering `handoff.md` directly, or starting implementation without invoking `--gate`. The architecture is therefore fail-closed **inside canonical helper calls**, but fail-open at the surrounding conversational/tool boundary.

Classification:

- **Prose policy:** `SKILL.md`, references, and the closed-loop guide specify actor behavior and transition order.
- **Policy decision logic (PDP):** ledger/protocol summaries, `session_status.next_action`, probe-level selection, and `implementation_gate.evaluate` compute allow/deny/next decisions.
- **Blocking enforcement (PEP):** Pydantic/typed delta validation plus atomic commit inside `session_update.py`, probe authorization validation, and `session_status.py --gate` exit `1` when that CLI is actually invoked.
- **Missing PEP:** there is no complete mediator around user-question emission, handoff delivery/copying, implementation dispatch, or arbitrary repo/tool mutation.

## PDP/PEP boundary assessment

The strongest separation is conceptual, not deployment-level:

1. `session_status`, `protocol_state`, `ambiguity_ledger`, `probe_policy`, and `implementation_gate` act as policy decision components.
2. `session_update` acts as the policy administrator/enforcement point for the files it owns: it validates before commit, rejects hand-setting managed fields, locks the session, journals the previous generation, commits all related files together, and recovers interrupted generations (`session_update.py:807-1021,1032-1127`; `atomic_write.py:47-55,91-125,134-193`).
3. `session_status --gate` fuses PDP and a narrow PEP: a deny produces process exit `1` (`session_status.py:411-441`). This blocks a shell pipeline that checks the exit status.
4. There is no policy administrator that turns a grant into a scoped capability/token and no gateway that requires that capability for handoff delivery, repo mutation, subagent implementation dispatch, or tool execution. Consequently, “only implementation_ready permits delivery” is prose outside the CLI process.

## Bypass suite that should exist

| Bypass attempt | Expected secure outcome | Current result |
|---|---|---|
| Ask another scored question after `--next` returns `budget exhausted` | Question-emission gateway denies unless an authenticated bounded extension exists | **Bypasses**: `--next` is advisory; a later event can still be booked |
| Send/copy `handoff.md` when `session_status --gate` would exit 1 | Delivery/implementation dispatcher refuses without a fresh grant bound to Part 1 digest | **Bypasses**: direct file/message/tool path is unmediated |
| Start `$ulw-loop` from Part 1 without running the gate | Executor refuses missing/denied readiness token | **Bypasses**: guide instructs order, but no coupling was found |
| Record `build_contract_test:{reviewer:"critic"}` without running critic | State writer rejects unverifiable reviewer evidence | **Passes structurally**: reviewer is only a nonblank string |
| Mark two self-produced evidence records with different independence groups | Independence validator rejects or requires authenticated lineage | **Potentially passes**: structural group uniqueness is checked, causal independence is self-asserted |
| Mark reflexive “all correct” as `fatigue:false` | Checkpoint credit denied based on independently observed fatigue/attention signal | **Passes structurally**: fatigue is supplied by caller |
| Record L3 authorization/result without actually owning approval or artifact | Runtime authorization service and artifact verifier deny | **Potentially passes structurally** if all bound strings and lineage shapes validate; the helper does not authenticate or run the probe |
| Modify a tracked requirement through `session_update` after review | Dry streak/checkpoint/review revoked deterministically | **Blocked correctly**: canonical mutation invalidates freshness |
| Edit Part 1 after review, then run `--gate` | Deny stale review and sidecar | **Blocked correctly** by digest/recompilation checks |
| Crash during multi-file state commit | Next canonical read restores one coherent prior generation | **Blocked/recovered correctly** by lock+journal transaction |

## Fail-closed, liveness, and fatigue tradeoffs

- **Safety strength:** strict schemas, unknown-field rejection, managed counters, atomic transactions, stale-digest checks, two dry sweeps, and exit-1 gate failures make canonical state corruption and false-ready *records* difficult.
- **Availability cost:** any malformed state, missing sidecar, unavailable command head on the current host, or unsupported non-POSIX host blocks readiness. There is no signed cached grant, degraded read-only gate mode, or policy-engine failover. A compromised or unavailable local PDP/PEP is a single point of denial.
- **Liveness escape hatches:** structured deferral, explicit budget extension, owner/delegated single-source acceptance, and abandoned-draft handoff let work continue. They are necessary, but weakly authenticated: ledger deferral accepts any nonblank owner/date strings, budget extension accepts any nonblank reason, and ownership/authorization is record data supplied by the same caller.
- **Fatigue control:** the two-free-follow-up cap is mechanically enforced, and a fatigue-flagged checkpoint receives no evidence credit. However, fatigue detection and the flag are not independent signals; the model that benefits from checkpoint credit decides whether the user looked fatigued. More checkpoints can therefore create both rubber-stamp risk and interview denial-of-service.
- **Best balance:** keep deterministic fail-closed behavior for state integrity and final readiness, but add mediation only at consequential boundaries: question emission after a denied `--next`, fresh-review attestation, handoff delivery/implementation dispatch, and L2/L3/tool execution. Use scoped, expiring, reason-coded human override rather than weakening ledger or digest gates. Do not continuously reauthorize every conversational token.

## Recommended concrete control split

| Component | Responsibility | Minimal implementation contract |
|---|---|---|
| Transition PDP | Evaluate `{subject, resource, action, context, policy_version}` for question, settlement, probe, review, finalization, dispatch | Pure deterministic result `allow|deny|revise|revoke` plus reason codes and input digest |
| State PEP | Own all session-state writes | Existing `session_update.py`; prohibit direct managed-file writes in orchestrated runs |
| Conversation PEP | Mediate scored-question/checkpoint emission | Require current `--next` grant bound to session generation and event type; consume once |
| Review PEP | Mediate `build_contract_test` | Require a reviewer completion artifact/session id and Part 1 digest, not only a reviewer name |
| Delivery/dispatch PEP | Mediate handoff copy/send and implementation start | Require `implementation_ready=yes` grant bound to session id, Part 1 digest, policy version, and short expiry |
| Runtime action PEP | Mediate L2/L3 and destructive/credentialed commands | External harness approval/capability; validate owner, scope, target, expiry, and command/action digest before execution |
| Revocation monitor | Reevaluate accepted state on relevant events | Watch ledger/Part 1/repo-source dependencies; revoke grants on digest change, contradiction, expiry, or failed verification |

Every Guardrail Compile `fast/pre-action` row should therefore name a resolvable PEP identifier and coverage attestation, not just `substrate:` prose. A final gate should fail when that PEP is absent, stale, or does not declare interception of the named action class.

## OBSERVATIONS

- The live scripts meaningfully enforce state consistency; calling them “just checklists” would be inaccurate.
- The decisive boundary is not PDP quality but reachability: canonical update and gate paths are strong, alternate conversation/file/tool paths do not pass through them.
- Material-change revocation is the closest current analogue to continuous diagnostics, but it is limited to state routed through `session_update`; there is no general evidence TTL or repo/source-change watcher.
- `interview_converged` is deliberately a stop condition, not an authorization. This separation is sound, but consumers can still use the handoff without the later authorization gate.
- The current system shifts trust to the interviewer process, local filesystem, helper code, caller-supplied provenance/authority, reviewer-name string, and downstream consumer discipline.

## CLAIMS

- **High confidence:** `session_update.py` is a real PEP for canonical session-state transitions because deny prevents commit and accepted updates are atomic/recoverable.
- **High confidence:** `session_status.py --gate` is a real but conditional PEP for its own CLI process; it is not a universal handoff or execution PEP.
- **High confidence:** `--next`, fatigue handling, endgame ordering, abandonment handling, and “only ready permits delivery” are not blocking enforcement outside the model’s compliance.
- **High confidence:** the largest zero-trust gap is absence of a grant consumed by the next consequential actor/path: question UI, handoff delivery, implementation dispatcher, or runtime tool wrapper.
- **Medium-high confidence:** adding universal mediation only at consequential transitions would improve safety without turning the interview into continuous reauthentication or worsening fatigue substantially.
- **High confidence:** zero-trust mediation would not validate truth, completeness, reviewer independence, or causal independence; those remain distinct evidence/assurance problems.

## EXPAND

- Trace the actual LazyCodex/ulw-loop invocation path and identify the narrowest dispatcher hook that can require a digest-bound readiness grant.
- Define a reviewer-attestation artifact and determine whether existing team/subagent session IDs can supply independently verifiable completion evidence.
- Add negative integration tests for the first seven bypasses above, especially direct handoff delivery and post-budget question emission.
- Specify event-triggered freshness for repo-derived evidence: file/content digest change, runtime observation age, source update, and explicit contradiction.
- Coordinate with evidence-authenticity/correlated-quorum work on authenticated source ownership and independence; PDP/PEP separation alone cannot solve them.
- Define fail-closed versus fail-operational behavior for PDP unavailability, including bounded human override, expiry, compensating controls, and audit log.
- Compile assurance-case defeaters into revocation transitions: a sustained rebutter reopens the claim, an underminer removes evidence eligibility, an undercutter removes the claim-evidence support edge, and an applicability failure invalidates the bound context/assumption.
